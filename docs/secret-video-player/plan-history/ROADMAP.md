## 2. 当前项目基线

### 2.1 已经具备的能力

当前安全视频子系统不是从零开始，已经形成四条可操作链路：

- **单文件加密**：将普通视频流式写为 SECVID03，显示进度，使用同目录 `.partial-*` 临时文件并在完整刷新后提交正式文件。
- **批量解密**：检查多个 SECVID03 文件，顺序导出明文，隔离单项失败，净化输出文件名并避免静默覆盖。
- **单文件播放**：通过可随机定位的按需解密流向 LibVLC 提供原视频视图，不生成完整明文临时视频。
- **文件夹媒体库播放**：扫描当前目录或递归子目录，监听增量变化，支持搜索、排序、状态筛选、播放历史和同页切换播放。

已有关键技术能力包括：

- SECVID03 使用 PBKDF2-SHA256 派生 256 位密钥，以 AES-256-GCM 认证固定头和 1 MiB 视频块。
- 固定头、原视频前缀和视频块受到密码学完整性保护；公开标题、描述和原始文件名明确视为不可信公开信息。
- `SeekableEncryptedVideoStream` 支持顺序读取与随机 Seek，并使用有限 LRU 明文块缓存控制内存占用。
- 加密和解密都采用事务式文件提交；失败、取消和关闭 Document 时进入半成品清理路径。
- 每个 Dock Document 使用独立 DI Scope，不共享任务状态、密码、播放位置或原生播放器实例。
- 部署探针从插件实际目录检查 Windows x64、托管桥接和私有 LibVLC；`LibVlcRuntime` 只消费通过的结果，不回退到工作目录、`PATH` 或系统 VLC。
- Dock 销毁并重建原生视频表面后，现有恢复策略能够恢复播放位置以及播放或暂停状态。
- 解密队列模型、公开信息和日志不持久化密码。
- 加解密已经共用预检严重级别、稳定失败代码和不覆盖输出事务；密码不进入任务或队列模型。

## 3. 总体实施原则

后续开发必须遵守以下顺序和边界：

1. **先验证安全与可靠性，再扩展功能**：P0 不增加大范围播放器功能，先把真实媒体、错误路径、资源释放和部署诊断变成可回归事实。
2. **SECVID03 格式冻结**：现有磁盘布局、KDF、分块、nonce 和 AAD 规则不在普通迭代中修改。若发现必须破坏兼容的安全问题，另行设计新魔数和专项计划。
3. **不支持 SECVID02**：不实现直接播放、批量迁移或兼容读取；P0 清理相关提示、旧格式辅助代码和迁移描述。
4. **密码永不落盘**：密码只存在于当前 Document 和同步调用链中，不进入任务模型、播放历史、设置、日志、诊断包或导出结果。
5. **Document 拥有任务生命周期**：不引入全局加解密 Coordinator 或持久化任务中心。关闭加密或解密 Document 时必须取消活动任务并清理当前半成品。
6. **任务提交必须是事务式的**：所有输出先写唯一 partial，验证、刷新和关闭成功后才以不覆盖方式提交正式文件。
7. **公开信息始终不可信**：公开标题、描述和原始文件名只用于展示与命名建议；路径生成、日志和 UI 都不能把它们当作经过认证的数据。
8. **播放不得生成完整明文副本**：倍速、全屏、连续播放、历史恢复等功能不得绕过按需认证解密流。
9. **用户操作优先于自动行为**：自动扫描和主加载按钮只定位、不自动播放；只有双击或 Enter 这种明确激活操作才允许恢复后起播。Dock 自动恢复不得覆盖用户刚执行的播放、暂停、停止或 Seek。
10. **平台能力显式化**：P0/P1 继续支持 Windows x64；P2 只建立可替换接口和 Windows 实现，不把“已抽象”等同于“已支持 Linux”。
11. **完成后再宣称支持**：只有同时通过代码、异常路径、自动化测试、手工验收和文档更新的能力，才能从“规划”改为“已实现”。

### G1：SECVID03 格式与安全验证

**时间：W2～W3，2026-08-03～2026-08-16**

**状态：已于 2026-07-23 提前完成。详细设计、威胁模型与验证记录：[G1-SECVID03-FORMAT-SECURITY-VALIDATION.md](G1-SECVID03-FORMAT-SECURITY-VALIDATION.md)**

主要工作：

- 编写 SECVID03 威胁模型，明确保护内容、攻击者能力、公开信息边界、密码内存边界和不抵御的场景。
- 生成固定测试向量，记录输入字节、公开信息、密码、固定头字段、块边界和预期认证结果。
- 覆盖空文件、短文件、整块、尾块、跨块读取、最大合法长度、物理文件截断、保留字段非零和整数溢出。
- 覆盖错误密码、固定头、原视频前缀、密文和 Tag 的独立篡改，以及公开区 CRC 损坏和合法重写。
- 验证结构检查早于高成本 KDF，畸形长度不会导致超大分配、越界 Seek 或路径写入。
- 基准记录 600,000 次 PBKDF2 的打开时延和 1 MiB 分块读取开销，不在 SECVID03 内静默更改参数。

退出条件：

- 格式文档、实现常量和测试向量一致。
- 任何受认证区域的单字节篡改都会被拒绝，公开区修改不会被错误宣称为密码学认证。
- 畸形、截断和溢出输入只产生受控错误，不提交输出、不泄漏文件句柄。
- 安全评审没有遗留必须破坏 SECVID03 兼容的未决问题；若存在，则停止后续功能并另立格式升级计划。

完成记录：

- 重新评估是否进入独立 Linux 适配项目；不得仅凭接口存在就宣称支持 Linux。

P2 统一退出条件：

- 平台相关职责可以由接口替换，Windows 实现通过全部回归。
- 业务层不再直接依赖 Windows HWND 和固定原生部署细节。
- 性能与资源释放基线稳定，诊断输出可用于实际排障且默认脱敏。
- 文档明确说明 Linux 原生表面、LibVLC 打包和发行验收均未交付。

## 8. 计划中的接口与数据边界

### 8.1 加解密任务接口

- 加密侧增加与 `IVideoDecryptionService` 对称的可测试服务接口。
- 加密和解密共用一致的任务状态、进度、预检严重级别和失败类别，但不强制合并为同一个执行服务。
- SECVID03 密钥派生、固定头认证和块认证继续保持内部实现，不作为插件公共扩展 API。
- 队列项目只保存路径、公开信息、状态、进度、输出和非敏感错误；密码由 Document 在执行调用时提供。
- 不新增全局 Coordinator、后台常驻队列或任务数据库。

### 8.2 播放能力接口

- 播放服务统一暴露播放状态、Seek、音量、倍速、全屏、音轨、字幕轨和媒体结束事件。
- ViewModel 只消费播放能力与平台能力，不直接操作 LibVLC 原生句柄。
- 单文件播放器与媒体库共用基础播放能力；上一项、下一项和连续播放只由拥有列表上下文的媒体库协调。

### 8.3 历史与设置接口

- 存储最近目录、递归选项、排序、侧栏状态、音量、倍速和播放位置。
- 文件身份至少结合规范化路径和可检测的文件变化信息，避免把同路径替换后的新文件直接当成旧媒体。
- 密码、密钥、明文块、认证上下文、公开描述全文和任务队列禁止写入历史。
- 支持删除单项、清空全部和处理损坏设置文件；损坏时回退默认值，不阻止播放器启动。

### 8.4 平台接口

- P2 增加 LibVLC 运行时定位与验证、视频表面适配和平台能力接口。
- Windows x64 是唯一生产实现；测试提供假运行时和假视频表面。
- Linux 原生视频表面、原生包部署和发行流程不属于本路线图交付范围。

## 13. 默认假设

- 仓库和插件名称以实际代码中的 `MySmallTools` 为准。
- SECVID03 是唯一容器格式并保持冻结；当前没有 SECVID02 存量数据，不提供兼容、迁移或直接播放。
- P0/P1 只面向 Windows x64；P2 只完成平台抽象和 Windows 实现，不交付 Linux 版本。
- 密码永不落盘，关闭加密或解密 Document 时安全取消自身任务。
- 播放历史允许以明文保存在当前用户数据目录，必须提供清除入口并明确隐私边界。
- 批量加密和解密默认顺序执行，不在本路线图中实现断点恢复、崩溃后任务恢复或后台常驻队列。
- 时间估算以一名全职开发者为基准，不包含法定假期、LibVLC/Avalonia 上游重大变化和路线图外插入需求。
- P0 结束后根据真实开发速度重新估算 P1/P2，产品安全边界和用户确认要求不随工期压缩而降低。
